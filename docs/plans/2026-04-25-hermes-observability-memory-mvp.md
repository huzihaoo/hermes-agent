## 执行摘要 (Executive Summary)

### 问题定义

当前 Hermes 是一个**功能完整但不可见**的 AI Agent 平台：
- ✅ 能完成任务
- ❌ 看不到为什么慢
- ❌ 不知道钱花在哪
- ❌ 记忆检索不准确
- ❌ 多用户场景性能差

**核心痛点：** 用户说"Agent 慢"时，我们只能猜，无法定位瓶颈。

### 战略目标

**不是修补，是重新定义 Agent 平台的基础设施。**

从 QCon 73 份工业级方案中学到：
- 可观测性不是锦上添花，是**生存必需**
- 记忆系统不是文件存储，是**智能索引**
- 多租户不是未来需求，是**当前瓶颈**

### 产品愿景

**3 个月后，Hermes 成为：**
1. **透明的 Agent** - 每个决策、每分钱、每秒钟都可见
2. **聪明的 Agent** - 记忆准确、学习快、不重复犯错
3. **可靠的 Agent** - 多用户并发、资源隔离、成本可控

### 商业价值

**对内（团队）：**
- 开发效率 +50%（快速定位问题）
- 运维成本 -30%（自动诊断）
- Token 成本 -20%（精准优化）

**对外（用户）：**
- 响应速度 +2x（并发优化）
- 任务成功率 +30%（记忆准确）
- 用户满意度 +40%（透明可控）

## 一、战略分析 (Strategic Analysis)

### 1.1 市场定位

**当前：** 内部工具（PNC Agent）  
**目标：** 企业级 AI Agent 平台

**竞品对比：**

| 维度 | Hermes (当前) | 蚂蚁 Vibe | 火山 Mem0 | 目标 |
|------|--------------|-----------|-----------|------|
| 可观测性 | ❌ 无 | ✅ 全链路 | ✅ Token 级 | ✅ 全链路 + Token 级 |
| 记忆系统 | ⚠️ 文件 | ✅ 向量 DB | ✅ 知识图谱 | ✅ 向量 + 演化 |
| 多租户 | ❌ 单用户 | ✅ 千人并发 | ✅ 企业隔离 | ✅ 百人并发 |
| 成本控制 | ⚠️ 事后统计 | ✅ 实时限额 | ✅ 自动优化 | ✅ 实时 + 告警 |

**差距：** 我们落后 1-2 代。

### 1.2 用户痛点（真实反馈）

**来自飞书群的抱怨：**
1. "Agent 又卡住了，不知道在干嘛" - 可观测性缺失
2. "这个月 Token 花了多少？" - 成本不透明
3. "为什么同样的问题要问两遍？" - 记忆不准确
4. "多个人同时用就变慢" - 并发瓶颈

**数据支撑：**
- 平均任务耗时：120 秒（其中 80% 时间不可见）
- Token 成本：$500/月（无法归因到具体任务）
- 记忆检索准确率：60%（关键词搜索）
- 并发上限：3 用户（超过后性能崩溃）

### 1.3 技术债务评估

**当前架构的三大问题：**

1. **单进程瓶颈**
   - Gateway 单进程处理所有请求
   - 无法水平扩展
   - 内存泄漏风险

2. **事件系统混乱**
   - 事件格式不统一
   - 无 Trace ID 关联
   - 日志散落各处

3. **记忆系统原始**
   - 基于 Markdown 文件
   - 无结构化索引
   - 无向量检索

**技术债务成本：**
- 每次故障排查：2-4 小时
- 每次性能优化：盲目尝试
- 每次新功能：担心破坏现有系统

## 二、产品方案 (Product Design)

### 2.1 核心原则

**1. 最小可行产品 (MVP) 优先**
- 不追求完美，追求可用
- 3 个月交付，不是 6 个月
- 每 2 周一个可演示的里程碑

**2. 用户价值驱动**
- 每个功能必须解决真实痛点
- 优先级 = 用户痛点 × 实现成本
- 不做"技术上很酷但用户不需要"的功能

**3. 渐进式改造**
- 不推倒重来
- 新系统与旧系统并存
- 逐步迁移，降低风险

**4. 数据驱动决策**
- 每个假设都要验证
- 每个优化都要量化
- 每个功能都要有指标

### 2.2 产品架构

#### 2.2.1 可观测性层 (Observability Layer)

**目标：** 让 Agent 的每个动作都可见

**核心组件：**

```
┌─────────────────────────────────────────────────────────┐
│                    Observability Layer                   │
├─────────────────────────────────────────────────────────┤
│                                                           │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐  │
│  │  Trace ID    │  │  Span Tree   │  │  Metrics     │  │
│  │  Generator   │  │  Builder     │  │  Collector   │  │
│  └──────────────┘  └──────────────┘  └──────────────┘  │
│         │                  │                  │          │
│         └──────────────────┴──────────────────┘          │
│                            │                              │
│                   ┌────────▼────────┐                    │
│                   │  Event Store    │                    │
│                   │  (SQLite)       │                    │
│                   └─────────────────┘                    │
│                            │                              │
│                   ┌────────▼────────┐                    │
│                   │  Dashboard      │                    │
│                   │  (Web UI)       │                    │
│                   └─────────────────┘                    │
└─────────────────────────────────────────────────────────┘
```

**数据模型：**

```python
# Trace: 一个完整的用户请求
class Trace:
    trace_id: str          # 唯一标识
    user_id: str           # 用户
    start_time: float      # 开始时间
    end_time: float        # 结束时间
    status: str            # success/error/timeout
    total_tokens: int      # 总 Token
    total_cost: float      # 总成本（美元）
    
# Span: Trace 中的一个步骤
class Span:
    span_id: str           # 唯一标识
    trace_id: str          # 所属 Trace
    parent_span_id: str    # 父 Span（嵌套）
    name: str              # 步骤名称（如 "tool:read_file"）
    start_time: float      # 开始时间
    duration: float        # 耗时（秒）
    metadata: dict         # 额外信息（如文件路径、Token 数）
```

**关键指标：**
- P50/P95/P99 延迟
- Token 消耗分布
- Tool 调用频率
- 错误率

#### 2.2.2 记忆系统 (Memory System)

**目标：** 从"文件存储"到"智能索引"

**架构：**

```
┌─────────────────────────────────────────────────────────┐
│                      Memory System                       │
├─────────────────────────────────────────────────────────┤
│                                                           │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐  │
│  │  Short-term  │  │  Long-term   │  │  Working     │  │
│  │  Memory      │  │  Memory      │  │  Memory      │  │
│  │  (Session)   │  │  (Vector DB) │  │  (Task)      │  │
│  └──────────────┘  └──────────────┘  └──────────────┘  │
│         │                  │                  │          │
│         └──────────────────┴──────────────────┘          │
│                            │                              │
│                   ┌────────▼────────┐                    │
│                   │  Memory Index   │                    │
│                   │  (Embeddings)   │                    │
│                   └─────────────────┘                    │
│                            │                              │
│                   ┌────────▼────────┐                    │
│                   │  Memory Engine  │                    │
│                   │  (Retrieval +   │                    │
│                   │   Evolution)    │                    │
│                   └─────────────────┘                    │
└─────────────────────────────────────────────────────────┘
```

**三层记忆：**

1. **短期记忆（Session Memory）**
   - 当前会话的上下文
   - 存储：内存（Redis）
   - 生命周期：会话结束后清除
   - 容量：最近 20 轮对话

2. **长期记忆（Long-term Memory）**
   - 用户偏好、历史任务、知识库
   - 存储：向量数据库（Qdrant/Chroma）
   - 生命周期：永久（除非用户删除）
   - 容量：无限

3. **工作记忆（Working Memory）**
   - 当前任务的临时上下文
   - 存储：SQLite
   - 生命周期：任务完成后归档
   - 容量：当前任务相关的所有信息

**记忆演化：**
- 自动合并相似记忆
- 自动遗忘低价值记忆
- 重要性评分（基于访问频率）

### 3.2 Phase A: 可观测性基础 (Week 1-2)

目标: 每个请求有 Trace ID, 每个步骤有耗时和 Token 成本

#### A.1 Trace/Span 数据模型

新增文件: gateway/observability/

gateway/observability/
├── __init__.py
├── trace.py          # Trace/Span 数据模型
├── collector.py      # 数据收集器
├── store.py          # SQLite 存储
└── middleware.py     # Gateway 中间件

核心实现 (trace.py):
- Span: span_id, trace_id, parent_span_id, name, kind, start_time, duration_ms, status, metadata
- Trace: trace_id, user_id, platform, request_summary, start_time, status, spans, total_tokens, total_cost_usd

存储 Schema (SQLite):
- traces 表: trace_id, user_id, platform, request_summary, start_time, end_time, status, total_tokens, total_cost_usd
- spans 表: span_id, trace_id, parent_span_id, name, kind, start_time, duration_ms, status, metadata, input_tokens, output_tokens, model, cost_usd

#### A.2 埋点位置

在 run_agent.py 中:
1. 任务开始时创建 Trace
2. 每次 LLM 调用创建 Span (kind="llm")
3. 每次 Tool 调用创建 Span (kind="tool")
4. 任务结束时关闭 Trace

改动文件清单:
- run_agent.py: +50 行 (Trace/Span 创建和关闭)
- model_tools.py: +20 行 (Tool 调用 Span 包装)
- agent/anthropic_adapter.py: +15 行 (LLM 调用 Span 包装)
- gateway/run.py: +10 行 (请求入口 Trace 创建)
- gateway/observability/: 新增模块

#### A.3 成本计算

pricing.py:
- claude-opus-4-6: input $15/1M tokens, output $75/1M tokens
- claude-sonnet-4: input $3/1M tokens, output $15/1M tokens
- gpt-4o: input $2.5/1M tokens, output $10/1M tokens

#### A.4 验收标准

- 每个请求有唯一 Trace ID
- 每个 LLM 调用有 Span (含 Token 和成本)
- 每个 Tool 调用有 Span (含耗时)
- 数据持久化到 SQLite
- hermes trace list 显示最近 Trace
- hermes trace show <id> 显示 Span 树
- 20+ 测试, 100% 通过

### 3.4 Phase C: 记忆系统升级 (Week 5-6)

## 六、决策记录 (Decision Log)

### D1: 可观测性存储选型

决策: SQLite (不用 Prometheus/Jaeger)

理由:
- 本地部署, 无需外部服务
- 与现有架构一致 (TaskStore, TemplateStore 都用 SQLite)
- 查询灵活 (SQL vs PromQL)
- 未来可导出到 Prometheus/Jaeger

### D2: 向量数据库选型

决策: ChromaDB (不用 Qdrant/Pinecone)

理由:
- 纯 Python, 无需额外进程
- 本地部署, 数据不出机器
- 与 OpenAI Embeddings 兼容
- 社区活跃, 文档完善

### D3: 并发控制方式

决策: 内存锁 + SQLite 配额 (不用 Redis)

理由:
- 单机部署, 不需要分布式锁
- 减少外部依赖
- SQLite 足够处理配额查询
